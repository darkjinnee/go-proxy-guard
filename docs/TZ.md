# Техническое задание: REST API сервис для аутентификации и авторизации на основе JWT токенов с последующим проксированием запросов

## Обзор системы

Сервис представляет собой reverse proxy с встроенной системой аутентификации на основе JWT (JSON Web Tokens). Сервис выполняет валидацию JWT токенов и проксирование авторизованных запросов к внутренним сервисам согласно конфигурации маршрутизации.

## Функциональные требования

1. **Генерация JWT токенов**: Поддержка генерации пары JWT токенов (access_token и refresh_token) с использованием различных алгоритмов подписи (HS256, RS256, RS512, ES256, EdDSA). Оба токена содержат стандартные claims (type, exp, iat) и пользовательские данные
2. **Обновление токенов**: Эндпоинт для обновления пары токенов на основе валидного refresh_token с генерацией новых токенов с обновленным временем жизни
3. **Защита от повторного использования refresh токенов**: Хранение использованных refresh токенов в Redis с TTL равным времени жизни токена для предотвращения повторного использования
4. **Валидация JWT токенов**: Проверка подписи, валидности, времени жизни и типа токена перед проксированием запросов. Принятие только access токенов для проксирования
5. **HTTP проксирование**: Проксирование валидированных запросов к целевым сервисам с сохранением исходного HTTP метода, заголовков и тела запроса
6. **Управление криптографическими ключами**: Генерация, хранение и управление приватными и публичными ключами для алгоритмов подписи
7. **Логирование операций**: Структурированное логирование всех операций с токенами и проксирования запросов

## API спецификация

### Эндпоинт генерации JWT токенов

**Метод**: `POST`  
**Путь**: `/api/v1/tokens/generate`  
**Content-Type**: `application/json`

Эндпоинт принимает JSON payload с метаданными токена (алгоритм подписи, тип токена) и claims (данные пользователя), генерирует два JWT токена (access_token и refresh_token) с использованием указанного алгоритма подписи и возвращает оба токена в ответе.

**Ограничение доступа**: Доступ к эндпоинту может быть ограничен по IP адресам через настройку `token.ip_whitelist` в конфигурации. Если whitelist указан, запросы с IP адресов, не входящих в список, отклоняются с кодом 403 Forbidden.

#### Структура запроса:  
**Request Body**:
```json
{
  "header": {
  "alg": "HS256",
  "typ": "JWT"
  },
  "payload": {
    "user_id": "12345",
    "username": "johndoe",
    "role": "admin"
  }
}
```

**Параметры**:
- `header.alg` (required): Алгоритм подписи токена. Должен быть из списка поддерживаемых алгоритмов в конфигурации
- `header.typ` (required): Тип токена. Должен быть из списка поддерживаемых типов в конфигурации
- `payload.*` (required): Claims токена (данные пользователя). Эти claims будут включены в оба токена (access_token и refresh_token). Поле `exp` из payload игнорируется, время жизни токенов берется из конфигурации

**Response** (HTTP 200 OK):
```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ0eXBlIjoiYWNjZXNzIiwidXNlcl9pZCI6IjEyMzQ1IiwidXNlcm5hbWUiOiJqb2huZG9lIiwicm9sZSI6ImFkbWluIiwiZXhwIjoxNzA1MzI0ODAwLCJpYXQiOjE3MDUzMjQwMDB9.signature",
  "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ0eXBlIjoicmVmcmVzaCIsInVzZXJfaWQiOiIxMjM0NSIsInVzZXJuYW1lIjoiam9obmRvZSIsInJvbGUiOiJhZG1pbiIsImV4cCI6MTcwNTkzMjgwMCwiaWF0IjoxNzA1MzI0MDAwfQ.signature"
}
```

**Структура токенов**:
Оба токена (access_token и refresh_token) содержат следующие стандартные claims:
- `type` (string, required): Тип токена. Значение `"access"` для access_token, `"refresh"` для refresh_token
- `jti` (string, required): Уникальный идентификатор токена (JWT ID) в формате UUID v4. Генерируется при создании токена и используется для идентификации токена в Redis при пометке как использованного. Каждый токен (access и refresh) получает свой уникальный jti
- `exp` (integer, required): Время истечения токена в формате Unix timestamp (секунды). Рассчитывается как текущее время сервера + время жизни токена из конфигурации
- `iat` (integer, required): Время создания токена в формате Unix timestamp (секунды). Текущее время сервера на момент генерации
- Все claims из `payload` запроса (например, `user_id`, `username`, `role` и т.д.)

**Время жизни токенов**:
- `access_token`: Время жизни берется из `token.exp` конфигурации (в минутах), конвертируется в секунды и добавляется к текущему времени
- `refresh_token`: Время жизни берется из `token.refresh_exp` конфигурации (в минутах), конвертируется в секунды и добавляется к текущему времени

**Ошибки**:
- HTTP 400 Bad Request: Некорректный формат запроса или неподдерживаемый алгоритм/тип
- HTTP 403 Forbidden: IP адрес клиента не входит в whitelist (если whitelist настроен в конфигурации)
- HTTP 500 Internal Server Error: Ошибка генерации токена (недоступен ключ, ошибка криптографии)

#### Алгоритм обработки запроса на генерацию токена:

1. **Проверка IP whitelist**: Если в конфигурации указан `token.ip_whitelist`, проверяется принадлежность IP адреса клиента к одному из указанных диапазонов. IP адрес извлекается из заголовка `X-Forwarded-For` (если присутствует) или из соединения напрямую. Если whitelist настроен и IP адрес не входит в список, запрос отклоняется с кодом 403 Forbidden
2. **Валидация запроса**: Проверка формата JSON, наличие обязательных полей `header.alg` и `header.typ`
3. **Проверка алгоритма и типа**: Валидация, что указанные алгоритм и тип поддерживаются сервисом (согласно `token.alg_supported` и `token.typ_supported`)
4. **Подготовка claims**: 
   - Получение текущего времени сервера в формате Unix timestamp (секунды) - `iat`
   - Генерация уникального идентификатора для access_token: `jti_access = UUID v4`
   - Генерация уникального идентификатора для refresh_token: `jti_refresh = UUID v4`
   - Расчет времени истечения для access_token: `exp_access = iat + (token.exp * 60)` (конвертация минут в секунды)
   - Расчет времени истечения для refresh_token: `exp_refresh = iat + (token.refresh_exp * 60)` (конвертация минут в секунды)
   - Объединение claims из `payload` запроса со стандартными claims (`type`, `jti`, `exp`, `iat`)
5. **Генерация access_token**: Создание JWT токена с claims: `{type: "access", jti: jti_access, ...payload, exp: exp_access, iat: iat}` с использованием указанного алгоритма подписи и ключа
6. **Генерация refresh_token**: Создание JWT токена с claims: `{type: "refresh", jti: jti_refresh, ...payload, exp: exp_refresh, iat: iat}` с использованием указанного алгоритма подписи и ключа
7. **Возврат токенов**: Оба токена возвращаются в ответе в формате JSON

### Эндпоинт обновления токенов (refresh)

**Метод**: `POST`  
**Путь**: `/api/v1/tokens/refresh`  
**Content-Type**: `application/json`

Эндпоинт принимает refresh_token, валидирует его и при успешной проверке генерирует новую пару токенов (access_token и refresh_token) с обновленным временем жизни, но с теми же данными пользователя из исходного токена.

**Ограничение доступа**: Доступ к эндпоинту может быть ограничен по IP адресам через настройку `token.ip_whitelist` в конфигурации (та же настройка, что и для эндпоинта генерации токенов).

#### Структура запроса:
**Request Body**:
```json
{
  "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ0eXBlIjoicmVmcmVzaCIsInVzZXJfaWQiOiIxMjM0NSIsInVzZXJuYW1lIjoiam9obmRvZSIsInJvbGUiOiJhZG1pbiIsImV4cCI6MTcwNTkzMjgwMCwiaWF0IjoxNzA1MzI0MDAwfQ.signature"
}
```

**Параметры**:
- `refresh_token` (string, required): JWT refresh токен, полученный при генерации или предыдущем обновлении токенов

**Response** (HTTP 200 OK):
```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ0eXBlIjoiYWNjZXNzIiwidXNlcl9pZCI6IjEyMzQ1IiwidXNlcm5hbWUiOiJqb2huZG9lIiwicm9sZSI6ImFkbWluIiwiZXhwIjoxNzA1MzI0ODAwLCJpYXQiOjE3MDUzMjQwMDB9.signature",
  "refresh_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ0eXBlIjoicmVmcmVzaCIsInVzZXJfaWQiOiIxMjM0NSIsInVzZXJuYW1lIjoiam9obmRvZSIsInJvbGUiOiJhZG1pbiIsImV4cCI6MTcwNTkzMjgwMCwiaWF0IjoxNzA1MzI0MDAwfQ.signature"
}
```

**Ошибки**:
- HTTP 400 Bad Request: Некорректный формат запроса (отсутствует refresh_token), размер refresh_token превышает `max_jwt_size_bytes`
- HTTP 401 Unauthorized: Refresh токен невалиден (отсутствует `jti`, неверный формат, неверная подпись), истек срок действия или уже использован
- HTTP 403 Forbidden: IP адрес клиента не входит в whitelist (если whitelist настроен в конфигурации)
- HTTP 500 Internal Server Error: Ошибка генерации токена (недоступен ключ, ошибка криптографии, ошибка подключения к Redis)

#### Алгоритм обработки запроса на обновление токенов:

1. **Проверка IP whitelist**: Если в конфигурации указан `token.ip_whitelist`, проверяется принадлежность IP адреса клиента к одному из указанных диапазонов. IP адрес извлекается из заголовка `X-Forwarded-For` (если присутствует) или из соединения напрямую. Если whitelist настроен и IP адрес не входит в список, запрос отклоняется с кодом 403 Forbidden
2. **Валидация запроса**: Проверка формата JSON, наличие обязательного поля `refresh_token`
3. **Проверка размера токена**: Проверка размера refresh_token в байтах. Если размер превышает `token.max_jwt_size_bytes`, запрос отклоняется с кодом 400 Bad Request. Проверка выполняется до декодирования токена
4. **Валидация refresh_token**:
   - Проверка формата токена (три части, разделенные точками)
   - Декодирование header и payload
   - Проверка наличия `jti` claim в токене. Если `jti` отсутствует, запрос отклоняется с кодом 401 Unauthorized (токен невалиден)
   - Проверка типа токена: `type` claim должен быть равен `"refresh"`
   - Проверка алгоритма подписи (должен соответствовать алгоритму в header)
   - Проверка подписи с использованием соответствующего ключа
   - Проверка времени жизни токена (`exp` claim должен быть больше текущего времени)
5. **Проверка использования токена**: Проверка в Redis, не был ли refresh_token уже использован. Ключ в Redis формируется как `refresh_token:<jti>`, где `jti` извлекается из payload токена. Если токен найден в Redis, запрос отклоняется с кодом 401 Unauthorized
6. **Извлечение данных пользователя**: При успешной валидации извлекаются все claims из payload токена, кроме служебных (`type`, `jti`, `exp`, `iat`)
7. **Генерация новых токенов**: 
   - Получение текущего времени сервера в формате Unix timestamp (секунды) - `iat`
   - Генерация уникального идентификатора для нового access_token: `jti_access = UUID v4`
   - Генерация уникального идентификатора для нового refresh_token: `jti_refresh = UUID v4`
   - Расчет времени истечения для нового access_token: `exp_access = iat + (token.exp * 60)`
   - Расчет времени истечения для нового refresh_token: `exp_refresh = iat + (token.refresh_exp * 60)`
   - Генерация нового access_token с claims: `{type: "access", jti: jti_access, ...user_data, exp: exp_access, iat: iat}`
   - Генерация нового refresh_token с claims: `{type: "refresh", jti: jti_refresh, ...user_data, exp: exp_refresh, iat: iat}`
8. **Помечение токена как использованного**: Сохранение использованного refresh_token в Redis с ключом `refresh_token:<jti>`, где `jti` - идентификатор использованного refresh_token из payload, и TTL равным времени жизни refresh_token из конфигурации (`token.refresh_exp` в секундах). Это предотвращает повторное использование токена
9. **Возврат новых токенов**: Новая пара токенов возвращается в ответе в формате JSON

**Защита от повторного использования**:
- После успешного использования refresh_token, его `jti` (JWT ID) сохраняется в Redis с ключом `refresh_token:<jti>` и TTL равным времени жизни refresh_token
- При попытке повторного использования токена, проверка `jti` в Redis вернет положительный результат, и запрос будет отклонен с кодом 401 Unauthorized
- TTL в Redis автоматически удалит запись после истечения времени жизни токена, что соответствует времени, когда токен все равно стал бы невалидным
- Использование `jti` вместо хэша токена обеспечивает стабильность ключей в Redis при изменении алгоритма подписи или структуры токена

### Валидация JWT токенов и проксирование запросов

**Метод**: `*` (любой HTTP метод: GET, POST, PUT, DELETE, PATCH и т.д.)  
**Путь**: `*` (любой путь согласно конфигурации маршрутизации)

Эндпоинт принимает HTTP запросы любого метода. JWT токен должен быть передан в HTTP заголовке `Authorization` в формате Bearer token.

#### Формат заголовка авторизации:
```
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyX2lkIjoiMTIzNDUiLCJ1c2VybmFtZSI6ImpvaG5kb2UiLCJyb2xlIjoiYWRtaW4ifQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

#### Алгоритм обработки запроса:

1. **Валидация Host header**: 
   - Проверка наличия и непустоты HTTP заголовка `Host` (или `:authority` для HTTP/2)
   - Если Host отсутствует или пустой → HTTP 400 Bad Request, обработка прекращается
2. **Проверка домена в конфигурации**: 
   - Нормализация домена (приведение к нижнему регистру, удаление порта)
   - Поиск домена в конфигурации `domains`
   - Если домен не найден → HTTP 404 Not Found, обработка прекращается
3. **Извлечение токена**: Сервис извлекает JWT токен из заголовка `Authorization` (формат: `Bearer <token>`)
4. **Проверка размера токена**: Проверка размера JWT токена в байтах. Если размер превышает `token.max_jwt_size_bytes`, запрос отклоняется с кодом 400 Bad Request. Проверка выполняется до декодирования токена
5. **Валидация токена**: 
   - Проверка формата токена (три части, разделенные точками)
   - Декодирование header и payload
   - Проверка типа токена: `type` claim должен быть равен `"access"` (refresh токены не принимаются для проксирования)
   - Проверка алгоритма подписи (должен соответствовать алгоритму в header)
   - Проверка подписи с использованием соответствующего ключа
   - Проверка времени жизни токена (`exp` claim должен быть больше текущего времени)
6. **Извлечение claims**: При успешной валидации извлекаются claims из payload токена (исключая служебные claims: `type`, `jti`, `exp`, `iat`)
7. **Добавление заголовков**: Claims добавляются в HTTP заголовки запроса в формате `X-JWT-<claim_name>` (например, `X-JWT-user_id`, `X-JWT-username`, `X-JWT-role`)
8. **Маршрутизация**: Определение целевого сервиса на основе конфигурации маршрутизации (домен из Host header, путь запроса)
9. **Проксирование**: HTTP запрос проксируется к целевому сервису с сохранением исходного метода, пути, заголовков и тела запроса

#### Коды ответов:

- **HTTP 200-599**: Ответ от целевого сервиса (проксируется без изменений)
- **HTTP 400 Bad Request**: Host header отсутствует или пустой, размер JWT токена превышает `max_jwt_size_bytes`
- **HTTP 401 Unauthorized**: Токен отсутствует, невалидный формат, подпись неверна, истек срок действия, тип токена не "access" или refresh токен использован повторно
- **HTTP 403 Forbidden**: Токен валиден, но IP адрес клиента не проходит проверку whitelist/blacklist
- **HTTP 404 Not Found**: Домен не найден в конфигурации или маршрут не найден для указанного домена
- **HTTP 408 Request Timeout**: Превышен таймаут при проксировании запроса
- **HTTP 502 Bad Gateway**: Ошибка подключения к целевому сервису
- **HTTP 504 Gateway Timeout**: Таймаут ожидания ответа от целевого сервиса

## Конфигурация маршрутизации

Конфигурация маршрутизации хранится в файле `configs/proxy.json`. Файл содержит маппинг доменов на правила маршрутизации для проксирования запросов после успешной валидации JWT токена.

**Важно**: Сервис обрабатывает запросы только для доменов, явно указанных в секции `domains` конфигурации. Запросы с доменами, не присутствующими в конфигурации, немедленно отклоняются с кодом 404 Not Found. Host header является обязательным, запросы без Host header или с пустым Host header отклоняются с кодом 400 Bad Request.

Конфигурация поддерживает:
- Группировку маршрутов по доменам (на основе HTTP Host header)
- Маршрутизацию по маскам путей (glob patterns)
- Фильтрацию по HTTP методам
- Фильтрацию по IP адресам (whitelist/blacklist)
- Переписывание путей (опционально)
- Добавление кастомных HTTP заголовков

#### Пример конфигурации:
```json
{
  "proxy": {
    "timeout": 5000,
    "default_headers": {
      "X-Powered-By": "MyProxy",
      "X-Env": "prod"
    }
  },

  "domains": {
    "api.example.com": {
      "routes": [
        {
          "match": {
            "path": "/v1/users/*",
            "method": ["GET", "POST"],
            "ip_whitelist": ["10.0.0.0/24", "192.168.1.0/24"]
          },
          "forward_to": {
            "url": "http://users-service.internal:8080",
            "add_headers": {
              "X-Service-Name": "users"
            }
          }
        },
        {
          "match": {
            "path": "/v1/orders/**",
            "method": ["*"]
          },
          "forward_to": {
            "url": "http://orders.internal:9000",
            "add_headers": {
              "X-Service-Name": "orders"
            }
          }
        }
      ]
    },

    "admin.example.com": {
      "routes": [
        {
          "match": {
            "path": "/admin/*",
            "method": ["*"]
          },
          "forward_to": {
            "url": "http://admin.internal:7000",
            "add_headers": {
              "X-Admin": "true"
            }
          }
        }
      ]
    }
  }
}
```

### Схема конфигурации

#### 1. Секция `proxy` — глобальные настройки проксирования
```json
"proxy": {
  "timeout_ms": 5000,
  "max_body_size_mb": 10,
  "default_headers": {
    "X-Powered-By": "Go-Proxy"
  }
}
```

- `timeout_ms` (integer, required): Максимальное время ожидания ответа от целевого сервиса в миллисекундах. Применяется ко всем проксируемым запросам, если не переопределено на уровне маршрута
- `max_body_size_mb` (integer, required): Максимальный размер тела HTTP запроса в мегабайтах. Запросы, превышающие лимит, отклоняются с кодом 413 Request Entity Too Large
- `default_headers` (object, optional): HTTP заголовки, добавляемые ко всем проксируемым запросам. Заголовки из этой секции имеют наименьший приоритет и могут быть переопределены заголовками из секции маршрута

#### 2. Секция `domains` — группировка маршрутов по доменам
Ключ объекта `domains` — это доменное имя (или wildcard паттерн), которое должно совпадать с HTTP Host header входящего запроса. Значение — объект с конфигурацией маршрутов для данного домена.

```json
"domains": {
  "api.example.com": { ... },
  "admin.example.com": { ... }
}
```

Каждый домен содержит массив `routes` с правилами маршрутизации.

#### 3. Секция `routes` — правила маршрутизации

Каждый элемент массива `routes` представляет одно правило маршрутизации со следующей структурой:
```json
{
  "name": "orders_api",
  "match": { ... },
  "forward_to": { ... },
  "options": { ... }
}
```

##### 3.1. Секция `match` — условия совпадения запроса с маршрутом

```json
"match": {
  "path": "/v1/orders/**",
  "method": ["GET", "POST"],
  "host_override": null,
  "ip_whitelist": ["10.0.0.0/24"],
  "ip_blacklist": ["192.168.1.100"]
}
```

**Параметры**:
- `path` (string, required): Glob паттерн для сопоставления пути запроса
  - `*` — соответствует одному сегменту пути (не включает символ `/`)
    - Пример: `/users/*` соответствует `/users/123`, но не `/users/123/profile`
  - `**` — соответствует любому количеству сегментов пути рекурсивно
    - Пример: `/api/**` соответствует `/api/v1/users`, `/api/v1/users/123`, `/api/v1/users/123/profile`
  - Обычные символы — точное совпадение
    - Пример: `/v1/users` соответствует только `/v1/users`
- `method` (array of strings, required): Список разрешенных HTTP методов. Значение `["*"]` разрешает все методы
- `ip_whitelist` (array of strings, optional): Список разрешенных IP адресов или CIDR сетей. Если указан, запросы с IP адресов, не входящих в список, отклоняются с кодом 403
- `ip_blacklist` (array of strings, optional): Список заблокированных IP адресов или CIDR сетей. Запросы с этих адресов отклоняются с кодом 403
- `host_override` (string, optional): Значение для подмены HTTP Host header перед проксированием запроса к целевому сервису. Если `null` или не указан, Host header сохраняется из исходного запроса

##### 3.2. Секция `forward_to` — конфигурация проксирования запроса

```json
"forward_to": {
  "url": "http://orders.internal:9000",
  "timeout_ms": 3000,
  "rewrite_path": "/orders/$1",
  "add_headers": {
    "X-Service": "orders"
  }
}
```

**Параметры**:
- `url` (string, required): URL целевого сервиса (upstream). Должен содержать схему (http/https), хост и опционально порт
- `timeout_ms` (integer, optional): Таймаут ожидания ответа от целевого сервиса в миллисекундах для данного маршрута. Если не указан, используется значение из глобальной секции `proxy.timeout_ms`
- `rewrite_path` (string, optional): Паттерн для переписывания пути запроса перед проксированием. Использует синтаксис `$1`, `$2`, `$3` для ссылки на захваченные группы из маски `path`. Если не указан, путь проксируется без изменений
- `add_headers` (object, optional): Дополнительные HTTP заголовки, добавляемые к проксируемому запросу. Имеют приоритет над заголовками из секции `proxy.default_headers`

## Глобальные настройки приложения

Глобальные настройки хранятся в файле `configs/app.json`.

```json
{
"proxy": {
  "timeout_ms": 5000,
  "max_body_size_mb": 10,
  "default_headers": {
    "X-Powered-By": "Go-Proxy"
  }
},
"token": {
  "exp": 1440,
    "refresh_exp": 10080,
  "max_jwt_size_bytes": 4096,
  "alg_supported": [
    "HS256",
    "RS256",
    "RS512",
    "ES256",
    "EdDSA"
  ],
  "typ_supported": [
      "JWT"
    ],
    "ip_whitelist": [
      "10.0.0.0/24",
      "192.168.1.0/24",
      "172.16.0.100"
    ]
  },
  "redis": {
    "host": "localhost",
    "port": 6379,
    "password": "",
    "db": 0,
    "key_prefix": "go-proxy-guard:"
  }
}
```

### Секция `proxy`

- `timeout_ms` (integer, required): Глобальный таймаут для всех проксируемых запросов в миллисекундах
- `max_body_size_mb` (integer, required): Максимальный размер тела HTTP запроса в мегабайтах
- `default_headers` (object, optional): HTTP заголовки, добавляемые ко всем проксируемым запросам

### Секция `token`

- `exp` (integer, required): Время жизни access_token в минутах. Используется для расчета `exp` claim в access_token (конвертируется в секунды и добавляется к текущему времени)
- `refresh_exp` (integer, required): Время жизни refresh_token в минутах. Используется для расчета `exp` claim в refresh_token (конвертируется в секунды и добавляется к текущему времени). Также используется как TTL для записи использованного refresh_token в Redis
- `max_jwt_size_bytes` (integer, required): Максимальный размер JWT токена в байтах. Токены, превышающие этот размер, отклоняются с кодом 400 Bad Request. Проверка выполняется до декодирования и валидации токена. По умолчанию: 4096 байт
- `alg_supported` (array of strings, required): Список поддерживаемых алгоритмов подписи JWT токенов. Должен содержать как минимум один алгоритм
- `typ_supported` (array of strings, required): Список поддерживаемых типов токенов. Должен содержать как минимум один тип
- `ip_whitelist` (array of strings, optional): Список разрешенных IP адресов или CIDR сетей для доступа к эндпоинтам генерации и обновления токенов. Если указан, запросы с IP адресов, не входящих в список, отклоняются с кодом 403 Forbidden. Если не указан или пустой массив, ограничений по IP адресам нет. Поддерживается формат:
  - Отдельные IP адреса: `"172.16.0.100"`
  - CIDR сети: `"10.0.0.0/24"`, `"192.168.1.0/24"`
  - IPv6 адреса и сети (если поддерживается): `"2001:db8::/32"`

### Секция `redis`

Настройки подключения к Redis для хранения использованных refresh токенов.

- `host` (string, required): Хост Redis сервера
- `port` (integer, required): Порт Redis сервера
- `password` (string, optional): Пароль для аутентификации в Redis. Если не указан, аутентификация не выполняется
- `db` (integer, optional): Номер базы данных Redis (по умолчанию 0)
- `key_prefix` (string, optional): Префикс для всех ключей в Redis. По умолчанию `"go-proxy-guard:"`. Используется для изоляции данных приложения в общем Redis инстансе

**Формат ключей в Redis**:
- Ключ для использованного refresh_token: `<key_prefix>refresh_token:<jti>`, где `jti` - уникальный идентификатор токена (JWT ID) из claim `jti` токена
- Значение: любое (например, `"1"` или timestamp использования)
- TTL: равен времени жизни refresh_token из конфигурации (`token.refresh_exp` в секундах)

**Преимущества использования JTI**:
- Безопасная идентификация токена: каждый токен имеет уникальный UUID, что позволяет надежно помечать токен как использованный
- Устойчивость к изменениям: при смене алгоритма подписи или структуры хэша, Redis ключи остаются валидными, так как основаны на неизменяемом `jti`
- Возможность отзыва токенов: наличие `jti` позволяет реализовать механизм отзыва конкретных токенов путем добавления их в Redis blacklist

## Управление криптографическими ключами

Все криптографические ключи (приватные и публичные) генерируются внутри контейнера при первом запуске сервиса и сохраняются на хост-машине через Docker volume mount.

### Структура хранения ключей

- **Путь на хост-машине**: `/var/lib/go-proxy-guard/keys/` (настраивается через переменную окружения `KEYS_DIR`)
- **Формат файлов**: 
  - HMAC ключи: `hmac_<key_id>.key` — один файл содержит секретный ключ в base64 кодировке
  - RSA ключи: `rsa_<key_id>.private` и `rsa_<key_id>.public` — отдельные файлы для приватного и публичного ключей в формате PEM
  - ECDSA ключи: `ecdsa_<key_id>.private` и `ecdsa_<key_id>.public` — отдельные файлы для приватного и публичного ключей в формате PEM
  - EdDSA ключи: `eddsa_<key_id>.private` и `eddsa_<key_id>.public` — отдельные файлы для приватного и публичного ключей в формате PEM
- **Идентификатор ключа**: UUID v4, генерируется при создании ключа

### Меры безопасности

- **Шифрование ключей**: Все ключи хранятся в зашифрованном виде с использованием алгоритма AES-256-GCM. Шифрование выполняется с использованием мастер-ключа (master key)
- **Мастер-ключ**: 
  - Передается через переменную окружения `MASTER_KEY` (приоритет) или через файл `master.key` в директории ключей
  - Должен быть длиной минимум 32 байта (256 бит)
  - При первом запуске, если мастер-ключ не задан, генерируется новый случайный ключ и выводится предупреждение в лог (ключ должен быть сохранен для последующих запусков)
- **Права доступа**: Файлы ключей создаются с правами доступа `0600` (только владелец может читать/писать)
- **Логирование**: Ключи никогда не логируются в открытом виде. В логах указывается только идентификатор ключа и алгоритм
- **Резервное копирование**: При генерации нового ключа создается резервная копия существующего ключа с тем же идентификатором (если существует) с суффиксом `.backup`

### Генерация и управление ключами

- **Автоматическая генерация**: При первом запуске сервиса автоматически генерируется набор ключей для всех алгоритмов, указанных в `token.alg_supported`. Для каждого алгоритма генерируется один ключ по умолчанию
- **Регенерация ключей**: Ключи можно регенерировать через административный API эндпоинт (требует аутентификации). При регенерации старый ключ сохраняется как резервная копия
- **Метаданные ключей**: Каждый ключ имеет следующие метаданные:
  - Уникальный идентификатор (UUID v4)
  - Алгоритм подписи
  - Дата и время создания (RFC3339)
  - Статус (active, deprecated, backup)

## Механизм маршрутизации по домену

Сервис использует HTTP заголовок `Host` (или `:authority` для HTTP/2) для определения домена и соответствующей конфигурации маршрутизации из файла `configs/proxy.json`.

### Алгоритм маршрутизации

1. **Извлечение домена**: Сервис извлекает значение HTTP заголовка `Host` (или `:authority` для HTTP/2) из входящего запроса
2. **Валидация Host header**: 
   - Если Host header отсутствует или пустой → HTTP 400 Bad Request с телом `{"error": "Host header is required"}`
   - Если Host header содержит только пробелы или невалидные символы → HTTP 400 Bad Request с телом `{"error": "Invalid Host header"}`
3. **Нормализация домена**: Домен приводится к нижнему регистру. Если в Host header указан порт (например, `api.example.com:8080`), порт удаляется перед поиском конфигурации
4. **Проверка наличия домена в конфигурации**: Выполняется поиск соответствующей секции в объекте `domains` конфигурационного файла. Поиск выполняется в следующем порядке:
   - Точное совпадение домена
   - Wildcard совпадение (если поддерживается, например `*.example.com`)
   - **Если домен не найден в конфигурации → HTTP 404 Not Found с телом `{"error": "Domain not configured", "domain": "<domain>"}`** (обработка запроса прекращается, дальнейшие проверки не выполняются)
5. **Применение правил маршрутизации**: Если конфигурация домена найдена, применяются правила маршрутизации из массива `routes` в порядке их объявления
6. **Обработка ошибок маршрутизации**: 
   - Если домен найден, но ни один маршрут не соответствует запросу → HTTP 404 Not Found с телом `{"error": "Route not found", "domain": "<domain>", "path": "<path>"}`
   - Если домен и маршрут найдены, но IP адрес клиента не проходит проверку whitelist/blacklist → HTTP 403 Forbidden с телом `{"error": "IP address not allowed", "ip": "<client_ip>"}`

**Важно**: Сервис обрабатывает запросы только для доменов, явно указанных в конфигурации `domains`. Любые запросы с доменами, не присутствующими в конфигурации, немедленно отклоняются с кодом 404 Not Found без выполнения валидации токена или других проверок.

### Пример обработки запроса

```
Входящий запрос:
  Method: GET
  URL: https://api.example.com/v1/users/123
  Headers:
    Host: api.example.com
    Authorization: Bearer <token>
    X-Forwarded-For: 192.168.1.100

Алгоритм обработки:
1. Валидация Host header: Host присутствует и не пустой ✓
2. Извлечение домена: api.example.com
3. Нормализация: api.example.com (уже в нижнем регистре, порт отсутствует)
4. Проверка домена в конфигурации: домен найден в domains["api.example.com"] ✓
5. Проверка маршрутов (по порядку):
   - Маршрут 1: path="/v1/users/*", method=["GET", "POST"]
     - Проверка path: /v1/users/123 соответствует маске /v1/users/* ✓
     - Проверка method: GET присутствует в списке разрешенных ✓
     - Проверка IP whitelist: 192.168.1.100 проверяется (если задан)
   - Маршрут найден
5. Проксирование:
   - URL целевого сервиса: http://users-service.internal:8080
   - Путь: /v1/users/123 (rewrite_path не указан, путь без изменений)
   - Добавление заголовков: X-Service-Name: users, X-JWT-user_id, X-JWT-username, X-JWT-role
   - Проксирование запроса
```

### Особенности реализации

- **Валидация Host header**: Host header является обязательным. Запросы без Host header или с пустым Host header отклоняются с кодом 400 Bad Request до выполнения любых других проверок
- **Белый список доменов**: Сервис обрабатывает запросы только для доменов, явно указанных в конфигурации `domains`. Запросы с доменами, не присутствующими в конфигурации, немедленно отклоняются с кодом 404 Not Found без выполнения валидации токена
- **Wildcard домены**: Поддержка wildcard паттернов в ключах `domains` (например, `*.example.com`). При наличии точного совпадения и wildcard совпадения, приоритет имеет точное совпадение
- **Порты в Host header**: Порты в Host header игнорируются при поиске конфигурации (например, `api.example.com:8080` → `api.example.com`)
- **Нормализация**: Домены приводятся к нижнему регистру перед поиском для обеспечения case-insensitive сопоставления
- **Кэширование**: Конфигурация доменов кэшируется в памяти после загрузки из файла для обеспечения быстрого доступа. При изменении файла конфигурации требуется перезагрузка сервиса или использование API для hot-reload (если реализовано)

## Система логирования

Все логи записываются в файлы на хост-машине через Docker volume mount с поддержкой автоматической ротации по размеру и времени.

### Конфигурация логирования

Настройки логирования хранятся в файле `configs/app.json` в секции `logging`:
```json
{
  "logging": {
    "level": "info",
    "output": "/var/log/go-proxy-guard/proxy.log",
    "rotation": {
      "max_size_mb": 100,
      "max_age_days": 7,
      "max_backups": 10,
      "compress": true
    },
    "format": "json"
  }
}
```

**Параметры конфигурации**:

- `level` (string, required): Уровень логирования. Допустимые значения: `debug`, `info`, `warn`, `error`
  - `debug`: Детальная информация о всех операциях, включая тела HTTP запросов и ответов (только для запросов размером < 1KB)
  - `info`: Основные операции: генерация токенов, валидация токенов, проксирование запросов, ошибки
  - `warn`: Предупреждения: невалидные токены, таймауты, недоступность целевых сервисов
  - `error`: Только критические ошибки: ошибки инициализации, ошибки криптографии, системные ошибки
- `output` (string, required): Абсолютный путь к файлу логов на хост-машине. По умолчанию: `/var/log/go-proxy-guard/proxy.log`
- `rotation` (object, required): Настройки автоматической ротации логов
  - `max_size_mb` (integer, required): Максимальный размер файла лога в мегабайтах перед ротацией. При достижении лимита текущий файл переименовывается с добавлением временной метки, создается новый файл
  - `max_age_days` (integer, required): Максимальный возраст файла лога в днях. Файлы старше указанного возраста автоматически удаляются
  - `max_backups` (integer, required): Максимальное количество архивных файлов логов для хранения. При превышении лимита удаляются самые старые файлы
  - `compress` (boolean, required): Включить сжатие архивных файлов логов с использованием алгоритма gzip. Сжатые файлы имеют расширение `.gz`
- `format` (string, required): Формат вывода логов. Допустимые значения: `json`, `text`
  - `json`: Структурированный JSON формат для последующего парсинга системами мониторинга и анализа
  - `text`: Человекочитаемый текстовый формат с временными метками и уровнями логирования

### Формат логов

#### JSON формат

Структурированный формат для интеграции с системами мониторинга и анализа логов (ELK, Loki, Splunk и т.д.).

**Пример записи лога (JSON)**:
```json
{
  "timestamp": "2024-01-15T10:30:45Z",
  "level": "info",
  "message": "Token validated and request proxied",
  "request_id": "req-12345",
  "domain": "api.example.com",
  "path": "/v1/users/123",
  "method": "GET",
  "client_ip": "192.168.1.100",
  "target_service": "http://users-service.internal:8080",
  "status_code": 200,
  "duration_ms": 45
}
```

#### Text формат

Человекочитаемый формат с временными метками в формате RFC3339.

**Пример записи лога (Text)**:
```
2024-01-15T10:30:45Z [INFO] Token validated and request proxied request_id=req-12345 domain=api.example.com path=/v1/users/123 method=GET client_ip=192.168.1.100 target_service=http://users-service.internal:8080 status_code=200 duration_ms=45
```

### События, подлежащие логированию

- **Генерация JWT токенов**: Метаданные (алгоритм, тип, идентификатор ключа, время жизни), без самого токена
- **Валидация токенов**: Результат валидации (успех/неудача), причина неудачи (неверная подпись, истек срок действия, неверный формат), идентификатор ключа
- **Проксирование запросов**: HTTP метод, путь, домен, IP адрес клиента, целевой сервис, HTTP статус код ответа, время выполнения запроса в миллисекундах
- **Ошибки**: Невалидные токены, таймауты, ошибки подключения к целевым сервисам, ошибки маршрутизации
- **Изменения конфигурации**: Перезагрузка файлов конфигурации (proxy.json, app.json), ошибки парсинга конфигурации
- **Операции с ключами**: Генерация новых ключей, загрузка ключей из файловой системы, ошибки доступа к ключам

### Требования безопасности при логировании

- **Токены**: JWT токены никогда не логируются полностью. В логах указывается только префикс токена (первые 10 символов) с суффиксом `...` (например, `eyJhbGciOi...`)
- **Ключи**: Секретные ключи, мастер-ключи и пароли никогда не логируются в любом виде
- **Тела запросов**: Тела HTTP запросов и ответов логируются только на уровне `debug` и только для запросов размером менее 1KB
- **Персональные данные**: Чувствительные данные из claims токенов (если таковые имеются) должны быть замаскированы или исключены из логов согласно политике безопасности

## Роутинг по маскам путей

Система использует glob-паттерны для сопоставления путей запросов с правилами маршрутизации. Поддерживается захват групп для переписывания путей при проксировании.

### Формат glob-паттернов

- `*` — соответствует одному сегменту пути (не включает символ `/`)
  - Пример: паттерн `/users/*` соответствует `/users/123`, но не соответствует `/users/123/profile`
- `**` — соответствует любому количеству сегментов пути рекурсивно (включая вложенные пути)
  - Пример: паттерн `/api/**` соответствует `/api/v1/users`, `/api/v1/users/123`, `/api/v1/users/123/profile`
- Обычные символы — точное совпадение с учетом регистра
  - Пример: паттерн `/v1/users` соответствует только пути `/v1/users` (не соответствует `/V1/users` или `/v1/Users`)

### Переписывание пути (rewrite_path)

Поле `rewrite_path` в секции `forward_to` используется для изменения пути HTTP запроса перед проксированием к целевому сервису.

**Важно**: По умолчанию все запросы проксируются с сохранением исходного пути. Поле `rewrite_path` является опциональным и применяется только при необходимости изменения пути.

### Синтаксис rewrite_path

- Используется синтаксис с плейсхолдерами `$1`, `$2`, `$3` и т.д. для ссылки на захваченные группы из паттерна `path`
- Группы захватываются автоматически:
  - `*` в паттерне создает одну группу, содержащую значение сегмента пути
  - `**` в паттерне создает одну группу, содержащую все сегменты пути после маски
  - Можно использовать явные группы в паттерне с синтаксисом регулярных выражений: `/api/v1/(.*)` → `$1` будет содержать все после `/api/v1/`

### Примеры использования rewrite_path

**Пример 1: Переписывание пути с использованием захваченной группы**

```json
{
  "match": {
    "path": "/api/v1/users/*"
  },
  "forward_to": {
    "url": "http://users-service.internal:8080",
    "rewrite_path": "/v1/users/$1"
  }
}
```

Входящий запрос: `GET /api/v1/users/123`  
Проксируется на: `http://users-service.internal:8080/v1/users/123`

Где `$1` содержит значение `123` (захваченное из маски `*`).

**Пример 2: Проксирование без изменения пути**

```json
{
  "match": {
    "path": "/api/**"
  },
  "forward_to": {
    "url": "http://backend.internal:8080"
  }
}
```

Входящий запрос: `GET /api/v1/users/123`  
Проксируется на: `http://backend.internal:8080/api/v1/users/123`

Поле `rewrite_path` не указано, путь проксируется без изменений.

### Алгоритм сопоставления маршрутов

Маршруты проверяются в порядке их объявления в массиве `routes` конфигурации домена. Применяется принцип "первый подходящий маршрут" (first match wins).

**Последовательность проверок для каждого маршрута**:

1. **Проверка соответствия пути**: Выполняется glob matching паттерна `match.path` с путем входящего запроса. Если не совпадает, маршрут пропускается
2. **Проверка HTTP метода**: Проверяется наличие HTTP метода запроса в массиве `match.method`. Если указано `["*"]`, проверка пропускается. Если метод не найден, маршрут пропускается
3. **Проверка IP whitelist/blacklist**: 
   - Если указан `ip_whitelist`, IP адрес клиента должен входить в один из указанных диапазонов
   - Если указан `ip_blacklist`, IP адрес клиента не должен входить ни в один из указанных диапазонов
   - Если проверка не пройдена, возвращается HTTP 403 Forbidden
4. **Применение rewrite_path**: Если все проверки пройдены и указано поле `rewrite_path`, путь запроса переписывается согласно паттерну
5. **Проксирование запроса**: Запрос проксируется к целевому сервису с применением всех настроек маршрута

### Описание модулей

#### `internal/auth/`
Модуль аутентификации и авторизации:
- Генерация JWT токенов (access_token и refresh_token)
- Валидация JWT токенов (проверка подписи, формата, времени жизни, типа токена)
- Извлечение и парсинг claims из токенов
- Интеграция с модулем управления ключами для получения ключей подписи
- Интеграция с модулем Redis для проверки использованных refresh токенов
- Обновление токенов (генерация новой пары токенов на основе refresh_token)

#### `internal/proxy/`
Модуль HTTP проксирования:
- HTTP reverse proxy с поддержкой всех методов (GET, POST, PUT, DELETE, PATCH и т.д.)
- Маршрутизация запросов на основе конфигурации
- Обработка заголовков (добавление, переписывание)
- Переписывание путей запросов
- Обработка ошибок и таймаутов

#### `internal/config/`
Модуль управления конфигурацией:
- Загрузка и парсинг JSON конфигурационных файлов
- Валидация структуры конфигурации
- Hot-reload конфигурации (опционально)

#### `internal/keys/`
Модуль управления криптографическими ключами:
- Генерация ключей для различных алгоритмов подписи
- Шифрование и дешифрование ключей с использованием мастер-ключа
- Работа с файловой системой (чтение, запись, резервное копирование)
- Управление метаданными ключей

#### `internal/logger/`
Модуль логирования:
- Настройка и инициализация системы логирования
- Ротация логов по размеру и времени
- Форматирование логов (JSON, text)
- Управление уровнями логирования

#### `internal/redis/`
Модуль работы с Redis:
- Подключение к Redis серверу
- Управление пулом соединений
- Сохранение использованных refresh токенов с TTL
- Проверка использования refresh токенов
- Обработка ошибок подключения и таймаутов

#### `cmd/proxy-guard/main.go`
Точка входа приложения:
- Инициализация всех модулей сервиса
- Загрузка конфигурации
- Запуск HTTP сервера
- Обработка сигналов для graceful shutdown
- Управление жизненным циклом приложения
