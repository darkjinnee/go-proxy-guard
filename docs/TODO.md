## Поддержка проксирования WebSocket

### Текущее состояние

WebSocket **не поддерживается**. Реализована только классическая HTTP-схема «запрос → ответ» с полной буферизацией тела запроса и ответа.

### Почему так

1. **`internal/proxy/proxy.go`** — прокси ходит в бэкенд через `http.Client.Do()` и читает ответ целиком (`io.ReadAll`). Для WebSocket после рукопожатия нужен долгоживущий двунаправленный поток и hijack соединения, а не один `Do()` с буферизованным телом ответа.

2. **`cmd/proxy-guard/handlers.go`** — handler всегда читает тело входящего запроса через `io.ReadAll` и отдаёт буферизованный ответ. Для `Upgrade: websocket` это несовместимо с типичным потоком handshake (нужен отдельный путь без полной буферизации upgrade-запроса как обычного HTTP body).

3. **`cmd/proxy-guard/main.go`** — у `http.Server` заданы `ReadTimeout` и `WriteTimeout` (15 с). Для долгих WS-сессий их обычно отключают или увеличивают для соответствующих маршрутов.

4. **Документация** (`README.md`, `docs/TZ.md`) описывает HTTP reverse proxy; WebSocket явно не входит в объём — это не запрет на доработку, просто в ТЗ и коде сейчас этого нет.

### Возможность реализации

Добавить поддержку **можно**. После той же JWT-валидации и маршрутизации нужна отдельная ветка для запросов с `Connection: Upgrade` и `Upgrade: websocket`.

Типичные шаги в Go:

- использовать **`net/http/httputil.ReverseProxy`** с корректным `Director` (стандартная библиотека умеет WebSocket), **или** ручной `Hijacker` + копирование между клиентом и апстримом;
- скорректировать **таймауты** сервера для WS;
- корректно проксировать **`Sec-WebSocket-*`**, при необходимости **`Host` / `X-Forwarded-*`**;
- решить, как передавать claims бэкенду (например, только в handshake через заголовки — аналогично текущим `X-JWT-*`).

Итог: архитектурно совместимо с идеей «сначала проверить JWT, потом отдать трафик дальше», но потребуются изменения handler’а, прокси-слоя и настроек сервера/таймаутов.
